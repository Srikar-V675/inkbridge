Project doc, draft 4, 16 Oct 2026

Inkbridge

A stroke-based canvas that any MCP agent can read from and write to, built as an end-to-end AI project for MSc applications.

Working name, rename freely Demo-ready by 31 Oct 2026 Solo, part-time, about 40 h

How to cross-check this doc. Claims are tagged verified (read in docs or repo while preparing this), reported (you tested it) or unverified (check on day 1). Section 11 lists the unverified items in the order to test them.

1The idea

A web canvas for handwritten notes, equations and diagrams. Every stroke stays as vector data. You select a region, and any MCP-capable agent (Claude Desktop, Claude Code) can inspect it: the ink, a cropped image, a transcription and its neighbours. The agent can also write back onto the canvas, as drafts you accept or reject.

One line: select any part of your handwritten canvas and let an agent read it, reason about it and answer next to it.

What it is for

This is a portfolio project, not a product. It should show one finished loop that touches front-end capture, a data pipeline, a vision-language model, a protocol server, agent tool design and a small evaluation. A finished and documented loop matters more than novelty.

2What unique thing we are solving

Agents on a canvas today get a picture of it. That is enough for a whiteboard of shapes, and weak for dense handwriting on a large canvas: a downscaled screenshot loses legibility, and there is no way to say "look at this part, at full resolution, with its strokes".

The claim, stated narrowly

The idea category is not new, and penecho proves people want it. The specific claim here is a representation: regions as persistent, addressable objects that return ink, image and text together. The testable version: an agent using region tools answers questions about a large handwritten canvas more accurately than an agent given one screenshot. The small evaluation in section 6 measures exactly that, and reports the result either way.

Search of existing work found no benchmark comparing raster, stroke and structured input for current frontier models on handwritten notes. That is a gap in what I found, not proof that none exists.

3How: the design decisions

DecisionWhy
Strokes are the truth; recognition is a cache. Transcriptions are keyed by a hash of the region's strokes and recomputed only when ink changes.A bad transcription never loses ink. Unchanged regions cost no API calls.
A region is the unit of access. In v1 a region is an explicit user selection saved with an ID. No auto-segmentation.Explicit selection is the strongest signal of intent and removes a hard research problem from a 16-day scope.
Three views per region: ink, image, text.VLM text can be wrong, so the agent can fall back to the image or the exact strokes.
Writes are drafts and append-only. Agent output is tagged, styled dashed and needs Accept or Reject. Write tools cannot edit or delete user ink.Safe by construction. Same pattern penecho uses for AI output.
Do not build a canvas. Embed Excalidraw.Free-draw, pen mode, selection, undo and export already exist and are MIT-licensed.
One recognizer function, behind Gemini free tier. A background worker transcribes each saved region and caches text, LaTeX and kind by stroke hash. The connected agent can still read the image itself, and corrections from you or the agent are stored as separate rows that win over Gemini.Search and preview text work without the agent opening every region. The model is a single string, so a paid model is a one-line swap.
No stroke generation. The agent writes text boxes, shapes, arrows and Mermaid diagrams, not handwriting.LLMs are poor at producing natural pen strokes, and it is not needed for the use cases.

4The whole flow

sequenceDiagram
  actor U as You on the tablet
  participant C as Canvas (Excalidraw)
  participant B as Backend (FastAPI + SQLite)
  participant M as MCP server
  participant A as Claude
  U->>C: write, then select a region
  C->>B: scene elements, region ids, crop PNG
  B->>B: store region, hash strokes
  B-->>B: Gemini transcribes crop, cached by hash
  A->>M: list_regions
  M->>B: read regions
  B-->>M: ids, kinds, bounds
  M-->>A: region list
  A->>M: get_region(id, image, ink)
  M-->>A: text, image, bounds, ink
  A->>M: write_text or draw_diagram
  M->>B: queue write op
  B->>C: WebSocket: add draft elements
  C-->>U: dashed draft appears
  U->>C: Accept or Reject
  1. Capture. You write with the stylus in pen mode. Excalidraw stores strokes as elements.
  2. Region. You select strokes and save them as a region. The client exports a crop PNG and sends elements, region and crop to the backend.
  3. Recognise (cached). A worker sends the crop to Gemini and stores text, LaTeX and kind, keyed by stroke hash. Unchanged regions are never re-sent.
  4. Ask. You talk to Claude in its own app. It calls MCP tools to list and read regions.
  5. Answer. Claude calls a write tool. The backend pushes draft elements to the canvas. You accept or reject.

Topology for the demo

The laptop runs the backend and the MCP server, and Claude Desktop or Claude Code runs there too. The tablet opens the web app over the home Wi-Fi at the laptop's LAN address. Everything is local; nothing is deployed publicly.

Checked on day 1. A page served over plain HTTP on a LAN address is not a secure context. Drawing, pen pressure, selection and export all worked there on the tablet, so no HTTPS setup is needed for v1. reported If a later feature needs a secure context, serve the dev server over HTTPS with a local certificate.

Limits: image width capped at 1024 px; ink points decimated to at most 5,000 per response; write tools reject any operation that targets an existing element. save_transcription writes only to the recognitions table, never to the canvas, and a user correction is never overwritten by an agent row.

Write-back

  • Agent elements carry customData: {author: "agent", draft: true, op_id} and a dashed style. reported that customData survives save and reload (Day-1 test).
  • Text uses the hand-drawn font. Diagrams come from Mermaid conversion.
  • Accept removes the draft flag. Reject deletes only that op's elements.
  • If Accept or Reject runs late: apply drafts directly through updateScene and rely on undo.

Evaluation (small, honest)

  • Set: 20 regions you write on the tablet: 8 handwriting, 6 equations, 6 diagrams. Minimum viable: 15 regions.
  • Metric 1, recognition: character error rate for text, normalised exact match for equations. If save_transcription is built, report Gemini and agent readings separately.
  • Metric 2, agent QA: 20 questions about one dense canvas. Condition A: whole-canvas screenshot. Condition B: region tools.
  • Report: one table and three failure examples in the README, whatever the result.

Non-functional

  • Local-first: no telemetry, no account. The Gemini key lives in an environment variable.
  • Free-tier content is used by Google to improve its products, so send only test and eval pages, never personal notes.
  • Recognition never blocks drawing and runs after an idle delay.
  • Out of scope: auto-segmentation, collaboration, auth, native Android, LaTeX rendering on canvas, handwriting generation, multi-page documents, public deployment, multi-agent orchestration.

Agent calls

10Input and output

Inputs

  • Pen strokes. Excalidraw freedraw elements: points and, if present, pressure.
  • Typed shapes and text. Same element format.
  • Region selection. A set of element ids saved by you.
  • Agent tool calls. JSON over MCP stdio.
  • Optional import. An .excalidraw file, such as your existing diagrams.

Outputs

  • To the agent. Structured JSON plus a PNG as image content.
  • To the canvas. Draft elements: text, shapes, arrows.
  • To disk. .excalidraw JSON and PNG export.
  • To the reader. Eval table, README, architecture diagram, 2-minute demo video.

Day-1 checklist (about 30 minutes)

  1. Open the embedded Excalidraw over the laptop's LAN address on the tablet. Draw with the stylus.
  2. Select a group of strokes. Read selectedElementIds and the matching freedraw elements, including any pressure array.
  3. Call updateScene to add a text element and a Mermaid flowchart.
  4. Add customData to an element, save, reload, and read it back.
  5. Export only the selection as a PNG.

All five pass: commit to Excalidraw. Stylus or customData fails: fall back to tldraw with a local-only demo, which keeps the same architecture.

Result, 16 Oct 2026: all five passed on the tablet, so Excalidraw is confirmed. Lasso in the npm build was not tested; box selection remains the fallback.
